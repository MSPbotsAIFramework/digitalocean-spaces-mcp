## Product design

### Goals / Non-goals

**Goals** (v1):
- Let an agent list, create, and delete Spaces buckets.
- Let an agent list objects in a bucket (with prefix/folder-style filtering and pagination).
- Let an agent read small objects directly, write objects, delete one or many objects, copy an object, and read an object's metadata (size, content type, ETag, last-modified) without downloading it.
- Let an agent obtain a short-lived, pre-signed URL for a GET or PUT on one object, for transfers too large to pass through a tool-call payload or for handing a direct link to a human/another system.

**Non-goals** (v1 — explicit cuts, see Decisions made by DEV01 for why):
- Bucket policies, bucket/object ACL management beyond a coarse create-time/put-time `private`/`public-read` choice, CORS configuration, lifecycle rules, static-website hosting, access logging configuration, and object versioning/tagging are out of scope.
- True multipart upload (resumable, chunked transfer of objects larger than this connector's single-call size cap) is out of scope; large files are handled by handing the caller a pre-signed PUT URL instead (see AC12).
- Cross-region object copy is out of scope — `spaces_copy_object` only copies within one region (DigitalOcean's `CopyObject` operates against one regional endpoint; cross-region duplication would require a download+upload round trip that this version does not implement).
- This connector does not implement credential encryption or audit logging itself — those are Agent Platform gateway properties applied to every connector uniformly.

### Acceptance criteria AC1..AC15

- **AC1**: Given the connector is running, When a client sends `tools/list` with valid credential headers, Then the response includes exactly the 10 `spaces_*` tools named in § Tech design · Data & API contract, each with a first-line description ≤ 100 chars and a full description ≤ 500 chars.
- **AC2**: Given a `tools/call` request missing any of the three required credential headers (access key, secret key, region), When any Spaces tool is invoked, Then the response is HTTP 401 and the body lists the missing header name(s) — the request never reaches DigitalOcean.
- **AC3**: Given valid credentials, When `spaces_list_buckets` is called, Then it returns every bucket owned by the account (name, creation date, region) and the tool is annotated `readOnlyHint: true`.
- **AC4**: Given valid credentials, When `spaces_create_bucket` is called with a bucket name and region, Then the bucket is created and the tool returns its name/region; Given a bucket name already taken globally, Then the response is a structured error (not a 500) distinguishable from a generic failure.
- **AC5**: Given valid credentials, When `spaces_delete_bucket` is called on an empty bucket, Then the bucket is deleted; Given the bucket still contains objects, Then DigitalOcean's "bucket not empty" condition is surfaced as a structured error telling the agent to empty the bucket first, not a bare 500.
- **AC6**: Given a bucket with more objects than one page, When `spaces_list_objects` is called with a `limit` and, on the next call, the returned `continuation_token`, Then the second call returns the next page and no object appears twice across the two pages; Given a `prefix`, Then only matching keys are returned.
- **AC7**: Given an object smaller than the configured size cap and a text-like content type, When `spaces_get_object` is called, Then it returns the object's content as text; Given an object over the cap (or non-text content), Then it returns metadata only (size, content type) plus a note to use `spaces_create_presigned_url` instead of raw bytes.
- **AC8**: Given a payload under the configured size cap, When `spaces_put_object` is called, Then the object is written and is immediately visible to `spaces_get_object_metadata`; Given a payload over the cap, Then the request is rejected with a structured `invalid_argument` error before any call reaches DigitalOcean.
- **AC9**: Given a list of 1 to many existing keys, When `spaces_delete_objects` is called, Then all listed keys are deleted in one call and the response reports per-key success/failure (deleting an already-absent key does not fail the whole batch).
- **AC10**: Given a source object and a destination bucket/key in the same region, When `spaces_copy_object` is called, Then the destination object exists with the source's content; Given a destination bucket that does not exist, Then the response is a structured `not_found` error.
- **AC11**: Given an existing object, When `spaces_get_object_metadata` is called, Then it returns size, content type, ETag, and last-modified timestamp without transferring the object body.
- **AC12**: Given valid credentials, When `spaces_create_presigned_url` is called with a method (`get` or `put`) and an expiry, Then it returns a URL signed for that single operation, valid only until the requested expiry, computed without any network call to DigitalOcean (pure local SigV4 signing).
- **AC13**: Given DigitalOcean returns HTTP 429 on any call, When a Spaces tool makes that call, Then the connector retries with backoff honoring `Retry-After` within the SOP's bounded retry budget; if still rate-limited after retries, the agent sees a structured `rate_limited` error, not a bare timeout.
- **AC14**: Given two concurrent `tools/call` requests carrying two different tenants' credential headers (different access key/secret key/region triples), When both complete, Then neither response contains data retrieved using the other request's credentials — verified by a concurrency test asserting no shared mutable state keyed only by in-process globals.
- **AC15**: Given the repository's `README.md`, Then it documents the three credential headers (purpose, where to obtain an access key/secret key pair, what region means), lists all 10 Spaces tools in its tool table, and its "MSPbots Connector" section is byte-for-byte identical to `~/.claude/skills/vendor-mcp-development/reference/readme-connector-section.md`.

## Tech design

### 1. Conclusion

Build a new Python 3.12 + `uv` + FastMCP service in the (currently empty) `MSPbotsAIFramework/digitalocean-spaces-mcp` repo, exposing 10 MCP tools over DigitalOcean's S3-compatible Spaces API. Each request carries its own access key / secret key / region in headers; the server uses `boto3`'s S3 client (created fresh per request, scoped via `contextvars`, never cached) to sign and send every call — reusing a mature, battle-tested SigV4 implementation instead of hand-rolling request signing, which is the single riskiest piece of this connector to get right.

### 2. Where the current implementation lives

Nothing exists yet. The repository has one commit on `main` (3d5b6c3): a two-line `README.md` — confirmed via `prepare_repo.py` and a direct read of the worktree. This is a from-scratch build (SOP "main line A"). There is no existing code in this repository to cite with `path:line`. The closest shape references are: the SOP's own template structure (`~/.claude/skills/vendor-mcp-development/SKILL.md` §A3) and the sibling `digitalocean-mcp` repo's design document (`docs/tickets/PRD-21343.md` on `origin/dev/PRD-21343`, read for comparison) — that repo's credential-header and tool-naming conventions are **not** reused here because Spaces' authentication is a different mechanism (SigV4 key pair vs. bearer token); reusing its single-header pattern would be wrong, not just inconsistent.

### 3. Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. `boto3` S3 client against DigitalOcean's Spaces endpoint | Treat Spaces as what it is — an S3-compatible store — and use AWS's own, widely-used Python SDK, pointed at `https://<region>.digitaloceanspaces.com` | SigV4 signing is exactly the hardest part of this API to get right by hand (clock skew, canonical request construction, payload hashing); `boto3` is maintained, tested, and DigitalOcean's own docs recommend S3-compatible tooling | One more dependency (`boto3` + `botocore`); synchronous client wrapped in a thread pool for the async server (boto3 has no native asyncio support) | **Chosen** |
| B. Hand-rolled SigV4 signer + raw `httpx` XML parsing | Implement the signature algorithm and parse the S3 XML responses directly | No synchronous-client-in-async-server friction | High risk of a subtly wrong signature implementation (silent auth failures are hard to debug); duplicates work `boto3` already does correctly; XML response parsing is extra surface area for bugs | Rejected — this is exactly the "selected self-build over mature open source" case the reuse rule warns against |
| C. `aioboto3` (async wrapper around boto3/aiobotocore) | Same SigV4 correctness as A, but native async | Avoids the thread-pool wrapper | Smaller, less-maintained dependency surface than `boto3` itself; aiobotocore trails botocore API-compatibility by varying amounts across versions | Rejected for v1 — the wrapper-thread-pool cost in A is small (Spaces calls are I/O-bound and infrequent per tool call); revisit if profiling shows contention |

No backend-vs-frontend trade-off applies (this is not a UI feature); the chosen library already is the industry-standard choice, matching the "reuse before build" ordering: `boto3` (mature library) over self-written signing (self-research/build).

- **Follow-ups to flag, not fix here**: none specific to this repo (it is not shared with other tickets, unlike `digitalocean-mcp`); if a future ticket wants bucket policy/CORS/lifecycle/versioning/tagging management, or true multipart upload, or cross-region copy, those are separate scope additions, not omissions in this design.

### 5. Data & API contract

**Credential headers** (all required on every `tools/call`):

| Header | Type | Required | Meaning |
|---|---|---|---|
| `X-DigitalOcean-Spaces-Access-Key` | str | yes | Spaces access key (Settings → API → Spaces Keys in the DO control panel) |
| `X-DigitalOcean-Spaces-Secret-Key` | password | yes | Spaces secret key, issued once alongside the access key |
| `X-DigitalOcean-Spaces-Region` | str | yes | Region slug of the Space being addressed (e.g. `nyc3`, `sfo3`, `ams3`, `fra1`, `sgp1`, `syd1`, `blr1`, `tor1`, `atl1`, `lon1`); passed through to DigitalOcean's endpoint construction, not validated against a hardcoded list (see Decisions made by DEV01) |

**Tools** (all names `spaces_<verb>_<resource>`, SOP-required annotations in parentheses):

| Tool | Params | Returns | Annotations |
|---|---|---|---|
| `spaces_list_buckets` | — | `[{name, region, created}]` | `readOnlyHint: true` |
| `spaces_create_bucket` | `name, region, acl?("private"\|"public-read", default "private")` | `{name, region}` | `readOnlyHint: false, idempotentHint: false` |
| `spaces_delete_bucket` | `name, region` | `{deleted: true}` | `readOnlyHint: false, destructiveHint: true` |
| `spaces_list_objects` | `bucket, region, prefix?, delimiter?, continuation_token?, limit?(default 50, max 200)` | `{objects: [{key, size, last_modified, etag}], common_prefixes: [...], has_more, continuation_token?}` | `readOnlyHint: true` |
| `spaces_get_object` | `bucket, region, key, max_bytes?(default 100000)` | small/text: `{content, content_type, size, truncated: false}`; otherwise: `{content: null, content_type, size, note: "use spaces_create_presigned_url"}` | `readOnlyHint: true` |
| `spaces_put_object` | `bucket, region, key, content(str, UTF-8 or base64), content_encoding("utf8"\|"base64"), content_type?, acl?("private"\|"public-read", default "private")` | `{key, etag, size}` | `readOnlyHint: false, idempotentHint: true` |
| `spaces_delete_objects` | `bucket, region, keys(1..1000)` | `{deleted: [key...], errors: [{key, code, message}]}` | `readOnlyHint: false, destructiveHint: true, idempotentHint: true` |
| `spaces_copy_object` | `source_bucket, source_key, dest_bucket, dest_key, region, acl?` | `{dest_bucket, dest_key, etag}` | `readOnlyHint: false, idempotentHint: true` |
| `spaces_get_object_metadata` | `bucket, region, key` | `{size, content_type, etag, last_modified, metadata: {...}}` | `readOnlyHint: true` |
| `spaces_create_presigned_url` | `bucket, region, key, method("get"\|"put"), expires_in_seconds?(default 3600, max 604800), content_type?(for put)` | `{url, expires_at}` | `readOnlyHint: true` (pure local signing, no network call) |

Error envelope (all tools, SOP §4 vocabulary): `{"error": {"code", "message", "retryable"}}`. Codes used: `not_configured` (missing header), `unauthorized` (bad access/secret key — DigitalOcean `AccessDenied`/`SignatureDoesNotMatch`), `invalid_argument` (bad bucket name, oversized payload, bad region format caught before the call), `not_found` (`NoSuchBucket`/`NoSuchKey`/copy destination missing), `rate_limited` (429/`SlowDown`, `retryable: true`), `upstream_error` (5xx after retries exhausted, `retryable: true`). `BucketNotEmpty` on `spaces_delete_bucket` is surfaced as `invalid_argument` with a message naming the bucket and instructing the agent to empty it first — chosen over inventing a new code outside the fixed vocabulary.

**Backward compatibility**: new connector, no prior contract to break.

### 6. Key flow / sequence

```
Agent (tenant) --tools/call(spaces_put_object, Headers: X-DigitalOcean-Spaces-{Access-Key,Secret-Key,Region})--> Gateway
  --HTTP, Headers forwarded--> digitalocean-spaces-mcp /mcp
    middleware: read 3 headers -> ContextVar(SpacesCredentials); any missing -> 401 (AC2)
    tool: validate args (size cap, AC8) -> client.py
      -> boto3.client("s3", endpoint_url=f"https://{region}.digitaloceanspaces.com",
                       aws_access_key_id=..., aws_secret_access_key=...)
      -> asyncio.to_thread(s3.put_object, Bucket=bucket, Key=key, Body=..., ACL=acl)
      -> botocore.ClientError on failure -> map to error envelope
    middleware: ContextVar.reset() in finally
<-- structured result or error -- Gateway <-- Agent
```

### 7. Non-functional

- **Idempotency & concurrency**: `boto3` S3 client is created fresh per tool call from the request-scoped `ContextVar`, never module-level or cached — no client instance, and therefore no credential, is ever shared across concurrent requests from different tenants (AC14). `spaces_put_object`/`spaces_delete_objects`/`spaces_copy_object` are naturally idempotent at the S3 protocol level (same PUT twice = same result; deleting an absent key succeeds).
- **Performance**: list/metadata calls are single round trips to DigitalOcean; `spaces_create_presigned_url` makes zero network calls (local signing only, sub-millisecond). Connect timeout 5s / read timeout 30s on every `boto3` call (via `botocore.config.Config`), consistent with every other MSPbotsAIFramework connector.
- **Security**: credentials never touch disk, environment variables, or logs — read from headers into a `ContextVar` and discarded at request end; `spaces_get_object`'s size cap (default 100 KB) prevents a single tool call from pulling an unbounded amount of tenant data through the LLM context; pre-signed URLs are scoped to one bucket/key/method and expire (max 7 days, the SigV4 protocol's own ceiling).
- **Multi-tenant isolation**: every credential is per-request (AC14); no tenant's access/secret key, nor any object content, is cached or shared across requests. The S3 "bucket" namespace is itself already tenant-scoped by whichever DigitalOcean account's keys are presented — the connector never infers or defaults a bucket on the caller's behalf.
- **Observability**: structured log line per tool call (tool name, bucket/key when applicable, DigitalOcean request id when the error path returns one, outcome code) with no credential values logged; this follows the same logging shape as the sibling `digitalocean-mcp` connector.

No test requires a real DigitalOcean account or network access — this connector needs no "needs a real vendor account" carve-out for its automated suite, though a manual smoke test against a real Space (if/when a test account becomes available) is recorded as a follow-up, not a blocker (SOP: lacking a vendor test account still publishes to INT as usual).

Regression face: none — new repository, nothing else depends on it yet.

### 10. Effort & breakdown

Story points: 3
Tier: cross-service flow / new subsystem, row "3" (not row "5") — new subsystem but bounded: no UI, no billing/usage metering, no notification/scheduling component, and no destructive-without-confirmation design (deletes require the agent to name exact keys, never a wildcard/bulk-by-prefix delete).
Considerations: 1 new repo/service (from scratch); external API is well-documented (official DigitalOcean reference + de facto S3 API) but this connector's auth mechanism (SigV4 key-pair signing via `boto3`) is new to this specific repo family — the one genuine unknown is how cleanly `boto3`'s synchronous client wraps into the async FastMCP server under load, not the API surface itself; writes (create/delete bucket, put/delete/copy object) and one destructive operation class (`spaces_delete_bucket`, `spaces_delete_objects`) are present and must map to non-500 structured errors; no data migration; multi-tenant isolation is mandatory and tested (AC14); no UI; 15 acceptance scenarios covering 10 tools plus cross-cutting header/retry/isolation/README checks.
Main uncertainty: exact throttling behavior (HTTP status and whether `Retry-After` is actually present) for DigitalOcean's Spaces endpoints specifically — AWS S3's own 503 `SlowDown` shape is assumed and documented as an assumption; if real throttling responses differ, the retry mapping in `client.py` needs a follow-up adjustment, not a redesign.
Order inside this ticket: 1) settings + middleware + client (credential plumbing, no tools yet) 2) read-only tools (list_buckets, list_objects, get_object, get_object_metadata, create_presigned_url) 3) write/delete tools (create_bucket, put_object, delete_objects, copy_object, delete_bucket) 4) README + container contract + full test suite.

### 11. Risks & dependencies

- **Risk**: `boto3`'s synchronous client wrapped in `asyncio.to_thread` could become a throughput bottleneck under concurrent tool calls from many tenants. Mitigation: Spaces tool calls are infrequent, I/O-bound, and short-lived compared to typical agent workloads; revisit with `aioboto3` (Option C) only if profiling in review or on INT shows contention.
- **Risk**: DigitalOcean Spaces' actual throttling response shape (status code, `Retry-After` presence) is assumed from AWS S3 compatibility, not independently confirmed against a live account (no test account available; per SOP, missing a vendor test account still publishes to INT as usual). Mitigation: the retry/backoff path is isolated to one function (`client.py`), so a mismatch is a small follow-up fix, not a structural problem.
- **Dependency**: none on another ticket or external team — this repo is not shared with any other ClickUp ticket (unlike `digitalocean-mcp`), and no gateway change is required.

- **TC10** (AC10): `spaces_copy_object` happy path; nonexistent destination bucket → `not_found`.
- **TC11** (AC11): `spaces_get_object_metadata` returns size/content-type/etag/last-modified without a body transfer.
- **TC12** (AC12): `spaces_create_presigned_url` returns a correctly-scoped, correctly-expiring URL with zero network calls.
- **TC13** (AC13): 429/throttling → retry with backoff honoring `Retry-After`; exhausted → `rate_limited`.
- **TC14** (AC14): two concurrent requests with different credential headers never cross-contaminate.
- **TC15** (AC15): README documents the 3 headers, all 10 tools, and the byte-identical Connector section.

### Decisions made by DEV01

- **Region is not validated against a hardcoded allow-list** — it is passed straight into `f"https://{region}.digitaloceanspaces.com"` and DigitalOcean's own DNS/connection failure (mapped to `upstream_error`) is the error signal for a bad region. Why: DigitalOcean has added Spaces regions over time (this design found 10+ already, e.g. ATL1/LON1/TOR1 are newer than the original NYC3/AMS3/SGP1 set); a hardcoded list drifts and becomes a trap exactly like the one this SOP's own history warns about for other hardcoded lists. Alternative not chosen: validate against a baked-in enum with a friendlier `invalid_argument` error — rejected because it needs maintenance this ticket has no mechanism to keep current.
- **`spaces_get_object` has a 100 KB inline-content cap, with `spaces_create_presigned_url` as the designed escape hatch for anything bigger** — not a raw-bytes-always or presigned-URL-always design. Why: returning arbitrarily large object bodies through an MCP tool call risks flooding the agent's context window with binary/large-text data (the same token-economy concern the SOP's A4 raises generally); a presigned URL lets the caller (or a downstream HTTP client) fetch large content directly without it ever passing through the LLM. Alternative not chosen: always return a presigned URL, never inline content — rejected because the common case (reading a small config/log/JSON object) is far more convenient inline, and the SOP explicitly favors tools being capabilities over mechanical API mirrors.
- **No multipart upload in v1** — `spaces_put_object` has a single-call size cap (documented in settings, not yet pinned to an exact number pending a review-leg sanity check against the gateway's own request-body limit) and anything larger must go through `spaces_create_presigned_url` with `method: "put"` instead. Why: true multipart upload (`CreateMultipartUpload`/`UploadPart`/`CompleteMultipartUpload`) is a stateful, multi-call protocol that does not fit a single synchronous MCP tool call well, and DigitalOcean's own presigned-URL mechanism already solves "upload something large" without it. Alternative not chosen: implement multipart as 3 separate tools (`spaces_create_multipart_upload`, `spaces_upload_part`, `spaces_complete_multipart_upload`) — rejected for v1 as unnecessary complexity until a ticket names a concrete need for resumable/chunked upload specifically (not just "large files").
- **Bucket and object ACLs are reduced to a binary `private`/`public-read` choice on create/put, with no separate `spaces_get_bucket_acl`/`spaces_put_bucket_acl`/CORS/lifecycle/versioning/tagging tools** — full S3 ACL/policy semantics (grantee lists, custom bucket policies, lifecycle rules, static website hosting, versioning, logging) are not exposed. Why: these are advanced, low-frequency administrative operations more naturally done once via the DO control panel than repeatedly via an agent tool call, and including all of them would push this connector toward (or past) the SOP's 20-tool ceiling for marginal agent value. Alternative not chosen: expose every bucket/object configuration operation DigitalOcean's API has — rejected as "API endpoint mirroring" rather than "capability design," which the SOP's A4 explicitly warns against.

## Self-test

### Implementation notes vs. the tech design

- **`errors.py`** was added beyond the original change list as a small shared module (`SpacesError`, the error-envelope serializer, and a compact `dumps()` helper) so `middleware.py`, `client.py`, and `tools.py` all build the same SOP §4 envelope instead of each hand-rolling JSON. No behavior beyond what the design specified.
- **SigV4 pinned explicitly**: `client.build_s3_client` sets `Config(signature_version="s3v4")`. Without it, botocore's default signer selection for a custom `endpoint_url` produced SigV2 query-string URLs (`AWSAccessKeyId=...&Signature=...`), which DigitalOcean Spaces does not accept — caught by `test_presigned_url_generation_makes_no_network_calls` failing against the wrong URL shape before this was added.
- **`spaces_list_buckets`'s `region` field**: DigitalOcean's `ListAllMySpacesBuckets` response reportedly carries a per-bucket `Region` extension that botocore's AWS-S3 model does not parse (it is not a standard AWS field). The implementation reads `bucket.get("Region")` and falls back to the requesting credential's own region when absent. This is a `[non-blocking, assumed]` gap flagged for review — only a real-account trace of the raw XML can confirm whether botocore surfaces it in any form; recorded as "Known limitations" in the README.
- **`spaces_get_object_metadata` / size-cap path in `spaces_get_object`** both use `head_object` only (never `get_object`), per AC11 and the token-economy rationale in AC7.
