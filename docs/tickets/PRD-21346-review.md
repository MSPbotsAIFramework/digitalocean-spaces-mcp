### Findings

1. [must-fix] src/digitalocean_spaces_mcp/tools.py:85,104,122,169,217,258,293,316,343 — every tool except `spaces_list_buckets` declares a `region` parameter (per the tech design's Data & API contract table and AC4/AC5/AC6/AC7/AC8/AC9/AC10/AC11/AC12), but the parameter is never used: each tool calls `build_s3_client(creds)` (client.py:36), which always builds the S3 client from the *credential header's* region (`creds.region`), never from the per-call `region` argument. `spaces_create_bucket` even echoes the unused argument straight back in its response (`dumps({"name": name, "region": region})`, tools.py:92) as if it had been honored. A single DigitalOcean Spaces access/secret key pair is valid across all Spaces regions for an account (it is not region-bound), so a caller legitimately supplying a different `region` per call (e.g. to manage buckets in `ams3` and `sfo3` with one credential set carrying `X-DigitalOcean-Spaces-Region: nyc3`) will silently have every call routed to the header's region instead, while the response claims the requested region was used. This contradicts AC4 ("the bucket is created" with the given region) and AC6/AC7/AC8/AC9/AC10/AC11's implicit "operates against the given bucket/region" contract. Fix: either build the S3 client's endpoint from the tool-level `region` argument (falling back to `creds.region` only when a tool omits it, e.g. `spaces_list_buckets`), or drop the parameter from every tool signature and document that one credential set is pinned to the header's single region — whichever the product intends — and update the tech design and tests (currently every test fixture passes `region="nyc3"` matching `creds.region`, which is why this was never caught) to lock in the real contract.
2. [must-fix] src/digitalocean_spaces_mcp/settings.py:18 — `get_inline_max_bytes` is set to 100,000 bytes, so `spaces_get_object` (tools.py:168-203) can return up to ~100 KB of inline text in a single tool result. SOP §14's "面向 Agent 设计" checklist is explicit: "单次返回 ≤ 20,000 字符" (`~/.claude/skills/vendor-mcp-development/reference/vendor-mcp-development-sop.md:477`). A 100 KB object is 5x over that ceiling and reproduces exactly the "flood the agent's context window" risk that "Decisions made by DEV01" cites as the reason for having a cap at all (`docs/tickets/PRD-21346.md` §Decisions, second bullet). Fix: lower `get_inline_max_bytes` to at or under the SOP's 20,000-character ceiling (accounting for JSON envelope overhead), or chunk/truncate with a `truncated: true` marker instead of returning the object whole.
